## 一、存储栈职责矩阵（定稿）

存储栈为**五存储**（Postgres / Qdrant / Neo4j / Elasticsearch / Redis）＋**可选 Ollama** 模型服务，与 `04_数据库设计.md §1` 一致。其中涉及命名（Collection / Key / 标签 / 索引）一律引用 04。

| 存储 | 版本约束 | 职责 | 关键约束 |
|------|----------|------|----------|
| Neo4j | 5.x community | 图谱唯一权威源（SSoT）：结构边 + 白名单域关系 + Community 节点 | 不自建全文索引（J5）；`canonical_name` 唯一约束 |
| Qdrant | ≥1.10 | 业务向量（按 doc_type 多 Collection，命名见 04 §3.1）+ `rag_cache`（L1 语义缓存，H2）+ `rag_episodic` 情景记忆 + 社区摘要向量（以 payload `community_id`/`level` 嵌入业务集合） | named sparse vectors；alias 蓝绿重建 |
| Redis | 7.x | 工作记忆 + 用户画像 + L2 精确检索缓存（Key 规范见 04 §4） | AOF 开启；volatile-lru；画像 key 无 TTL |
| Elasticsearch | 8.x + IK 插件 | 实体（name/description/aliases）+ chunk 正文全文索引（索引见 04 §6） | `_id` = `entity_id` / `chunk_id`（与 04 §6.2/§6.3 三方一致）；异步同步 + 死信队列 |
| PostgreSQL | 16.x | langgraph thread checkpoint（会话状态权威源，J21）+ `doc_documents` 管道清单（04 §2.3）+ feedback 自建表（见 2.6） | 业务面对 checkpoint 只读 |
| Ollama | 可选 | 仅本地模型 Profile B 时启用 | GPU 直通、模型卷持久化 |

## 二、八项遗留问题设计裁决（讨论成果）

### 2.1 TTL 职责重定义

数据新鲜度**完全由事件失效保证**；TTL 只承担容量回收职责。L1=3600s、L2=600s 维持 04 原值，不再视为倒挂缺陷——两个机制各司其职：事件失效管「对不对」，TTL 管「占不占地方」。04 §7.1 已列 TTL 总表，本文补充其背后的失效触发机制（见 2.2 / 2.8）。

### 2.2 L1 缓存 payload 契约与反查失效

"按 doc_id 反查受影响缓存条目"（架构第 9 层）此前缺少实现载体，定稿如下（字段以 `04 §3.3` 为准）：

```text
L1 条目 payload = {
    question: str,
    answer: str,
    citations_json: list[Citation],
    matched_doc_ids: list[str],   # 由 Citation.result_ids → RetrievalResult.doc_id 聚合
    model: str,
    created_at: int(unix)
}
```

- Qdrant 对 `matched_doc_ids` 建 **keyword 数组 payload index**（04 §3.3 已定义该字段）
- 失效流程：updater 删除/更新事件 → `filter(matched_doc_ids contains doc_id)` scroll + delete（与 04 §7.2 文档删除联动衔接）
- 三条边界：
  1. 无引用答案（chitchat 直答、Web 来源）无 doc_ids，靠 TTL 过期——可接受；
  2. 增量更新走「先删后建」，「内容改写但 doc_id 不变」场景已被删除事件覆盖；
  3. 证据含社区摘要时，社区重算触发同样按 `community_id` 反查失效。

### 2.3 图 Schema 统一约定【D6】

消解 J12 与 G4 的标签矛盾（与 `04 §5` 保持一致）：

- **双标签**：基标签 `Entity` + 类型标签 `{Dish, Ingredient, Step, Technique, Other}`
- MERGE 键 = `canonical_name`（G4），唯一约束 `UNIQUE(e.canonical_name)`
- 结构边与白名单域关系**并存**：
  - 结构边：`[:MENTIONS {evidence_span}]`（04 §5.2，支撑 Local Search 子图扩展与反查溯源）
  - 白名单域关系（G1/G3 LLM 抽取产出）：`(:Dish)-[:REQUIRES]->(:Ingredient)`、`(:Dish)-[:HAS_STEP]->(:Step)`、`(:Technique)-[:APPLIES_TO]->(:Dish)` 等，以 `config/graph_schema.yaml` 为准
  - 开放区泛化关系：`[:REL {weight}]`（04 §5.2），`weight` 由 **PMI** 计算【D5】，Local Search 二跳扩展时加 PMI 阈值过滤
- 开放区实体统一标 `Other` 入开放区，经 admin 审核队列升级进白名单（J12 升级机制）
- 新增配置文件：`config/graph_schema.yaml`（白名单+开放区规则）、`config/entity_aliases.yaml`（别名表）

### 2.4 Qdrant Collection 规范

命名严格遵循 `04 §3` 的 `rag_<用途>` 前缀；废弃单库 `graphrag_docs` 方案，按 doc_type 一型一集合：

| Collection | 内容 | 说明 | 对齐 04 |
|------------|------|------|---------|
| `rag_recipes` / `rag_tips` / `rag_knowledge` | 按 doc_type 分业务向量库 | dense+sparse 双 named vector | 04 §3.1 |
| `rag_cache` | 语义缓存 | ANN top-1 ≥0.95 命中（H2） | 04 §3.3 |
| `rag_episodic` | 情景记忆 | metadata 含 session_id/user_id/timestamp | 04 §3.2 |
| （社区摘要） | 嵌入业务集合的 point | `source="global"`，metadata 含 `community_id`/`level` | 04 §3.1 payload 键 |

- sparse named vector 配置统一（04 §3.1）
- **重建走 alias 原子切换**：写新版本 collection → 切 alias → 删旧库（落实 P6「版本管理/支持回滚」；概念同 04 §6.4 ES 别名蓝绿）
- updater 删除时跨全部业务 collection 按 doc_id payload filter 清理（衔接 04 §7.2）

### 2.5 ES 落地细节【D9】

- docker-compose 新增 elasticsearch 服务（镜像含 IK，安装方式见第六章未定案）
- es_syncer 内嵌 graph_indexer：图谱写入成功后异步同步 ES；失败入 **Redis List 死信队列**（admin 可重放）——与 `04 §6.4`「失败入重试队列，死信人工介入」一致
- `_id` 映射规范：`entity_id` / `chunk_id`（裸值，与 04 §6.2/§6.3 一致，三方一致）
- es_retriever 容忍「ES 命中但 Neo4j 已删」的秒级窗口（回查为空则 null-skip），一致性最终以 Neo4j 为准

### 2.6 Postgres 边界

- thread checkpoint 表由 langgraph SDK checkpointer 自动托管迁移（04 §2.1），业务面代码只读不写
- `POST /feedback` 落库需要 app 自建表、自管 migration（与 checkpoint 同库不同 schema）；**该 feedback 表 schema 04 未覆盖，列为未定案（第六章）**
- `GET /sessions/{id}/messages` 聚合 PG checkpoint（`runs` 表，04 §2.1）与 Redis 工作记忆两源，去重以 checkpoint 为准

### 2.7 precheck Embedding 归属【D4】

J22 把 L1 查询放在业务面（FastAPI `POST /chat/precheck`），而 J3/H1 定案 BGE-M3 进程内加载于 langgraph-server。定案：**FastAPI 与 langgraph-server 各自进程内加载一份 BGE-M3**（各 ~1-2GB 显存/内存），单机最简方案，不引入 TEI。未来多实例横向扩展时再评估 TEI 共享。

### 2.8 生命周期簿记

- episodic collection 的 session_id/user_id 字段建 payload index（隔离过滤与删除的前提，04 §3.2 已定义）
- `DELETE /sessions/{id}` 联动批量删除对应情景记忆点（04 §3.2 / §7.1）
- Qdrant 无原生 TTL → 定时任务按 `created_at` filter 清理；在 04 §7.1 的「随会话删除」基础上**补充默认保留 180 天**的兜底清理
- 社区双写以 **Neo4j 为权威**：`(:Community)` 存 member_count/changed_count，admin 任务扫描判定变更实体占比 >20% 触发重算（J14）；重算完成联动 L1 缓存失效（衔接 2.2 反查机制）

## 四、分阶段实施计划（映射 v3.0 路线图阶段 0-3）

### Phase 0 环境（约 0.5 天）

| 任务 | 文件 | 内容 |

| 0.4 数据契约 | app/core/models.py | 模型族落地（RawDocument→EnrichedChunk、RetrievalResult、Citation 等） |

### Phase 1 客户端层（约 1 天）— TODO 清零

| 文件 | 关键实现要点 |
|------|--------------|
| redis_client.py | 连接管理、set(ex=ttl)、scan_and_delete(pattern)、死信队列 List 操作 |
| qdrant_client.py | gRPC 连接、named sparse vectors 建库、alias 创建/切换操作、payload filter scroll+delete |
| neo4j_client.py | driver + verify_connectivity、ensure_constraints（canonical_name UNIQUE、chunk/doc RANGE 索引）、别名归一化查询、PMI 过滤扩展 |
| es_client.py（新建） | IK 索引管理、bulk 同步、按 `_id` 删除、健康检查 |

验收：四个 check_health 对 docker compose 服务全部返回 True。

### Phase 2 图谱构建 P7（约 2 天）

顺序：schema.py（加载校验 graph_schema.yaml）→ entity_resolver（G2：规范化+别名表+向量聚类 >0.92 合并/[0.80,0.92) 灰区审核队列）→ relation_extractor（LLM few-shot，extractor 角色条目）→ graph_writer（双标签 MERGE 幂等写入）→ community.py（Leiden）+ summarizer（分层摘要）。

规则+字典实体抽取作为 G2 兜底保留（config/entity_aliases.yaml + 高频词表）。

验收：抽样 10 个 HowToCook 文档跑管道——双标签正确、别名归一生效、灰区实体进审核队列、社区树生成且 (:Community) 带 member_count。

### Phase 3 索引与失效联动 P6（约 1.5 天）

| 任务 | 内容 |
|------|------|
| vector_indexer | 按 doc_type 路由写入 `rag_*` 业务集合、dense+sparse 批量 upsert |
| graph_indexer 内嵌 es_syncer | 写图成功→异步同步 ES→失败入 Redis 死信 |
| fulltext_indexer 改造 | 由 Neo4j Lucene builder 改为 ES index builder |
| updater 三清 | Qdrant 各 `rag_*` 集合 filter 删 + Neo4j DETACH DELETE 子图 + ES 按 `_id` 删 |
| 失效联动 | 三清完成后按 `matched_doc_ids` 反查 L1 条目（04 §3.3 `rag_cache`）删除；社区重算联动同机制 |

验收：修改一个菜谱 md → incremental_update → 向量/图谱/ES 三处一致更新、引用该文档的 L1 缓存条目被清除。

### Phase 4 记忆层 J17（约 1.5 天）

| 文件 | 内容 |
|------|------|
| working_memory.py | Redis List 滑动窗口 + LTRIM + EXPIRE（Key 见 04 §4 `wm:{session_id}`） |
| episodic.py | 情景记忆向量化入库/相关性检索/payload index/180 天清理任务 |
| scheduler.py | 注入决策（工作记忆全文 + 情景 top-k）+ 双重去重 |
| user_profile.py | 画像 Hash 无 TTL + summaries List LTRIM 20 + 定期蒸馏 |
| semantic_cache.py | L1=Qdrant ANN≥0.95 + single-flight + payload 契约（2.2，集合 `rag_cache`）；L2=Redis 精确 hash（04 §4 `l2:ret:`） |

配套：FastAPI `POST /chat/precheck` 接双进程 embedding（D4）。

验收：相似问句命中 L1；带个性化上下文的答案不入缓存；DELETE 会话后情景记忆清零。

## 五、决策记录（续编）

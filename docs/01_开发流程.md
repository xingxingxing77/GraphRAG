## 4. Git 工作流

### 4.1 分支模型

```
main            ← 可发布，仅接受 PR，保护分支
develop         ← 集成分支，CI 必须绿
feature/<子阶段编号>-<模块>-<描述>   例: feature/3.2-es-syncer、feature/10.2-auth-endpoints
fix/<缺陷号>-<简述>            例: fix/142-citation-marker-offset
docs/<主题>
```

- **分支名前缀 = §6 子阶段编号（x.y）**，与任务单元一一对应；一个分支对应一个可独立验收的单元（S1/S2/S3 可拆多个 PR，但共享同一分支）
- 分支存活 ≤ 5 个工作日，超期强制 rebase 拆分

### 4.2 提交规范（Conventional Commits）

```
<type>(<scope>): <subject>

type ∈ feat | fix | docs | refactor | test | chore | perf
scope ∈ api | agent | retrieval | pipeline | memory | web | db | infra
示例:
feat(agent): A2 reflect short-circuit conditional edge
fix(api): precheck 返回建议 run 参数缺失 latency_tier 默认值
```

- `feat`/`fix` 合入 develop 必须关联里程碑任务号；commit message 中文 subject 允许

### 4.3 Code Review 规则

- 至少 1 名同角色 + 1 名跨角色评审（契约改动必须跨角色：改 02 的 PR 需前后端各一人 approve）
- 评审清单：契约一致性 → 降级路径覆盖 → 测试齐全 → 无明文密钥 → 决策编号引用正确

## 5. CI/CD 流水线

```
push/PR → lint(ruff,eslint) → typecheck(mypy,tsc)
        → unit tests(pytest,vitest)
        → golden set 回归(仅触及检索/分块/清洗/模型的 PR; D8 门禁)
        → build(docker images / vite build) → deploy(staging 自动, main 手动发布)
```

- **回归门禁**（D8）：Recall@5 或 Faithfulness 相对基线下降 >3% → 阻断合并
- **无变更时**每周定时跑一次全量 golden set 防退化
- 构建产物：`app`、`langgraph-server` 两镜像 + 前端静态资源

## 6. 实施里程碑与三步工作流

顶层阶段编号与架构文档第十一章保持一致（0-10），保证 07 的 F1-F4、批次 L1-L4 等跨文档引用稳定。每个阶段拆分为若干**子阶段任务单元**（编号 `x.y`）；任何单元一律先执行 **§6.0 三步工作流**，再谈准出。

### 6.0 标准任务单元三步工作流（所有子阶段强制遵循）

| 步骤 | 动作 | 强制要求 |
|------|------|----------|
| **S1 后端实现** | 先完整读取本单元「前置阅读」列出的章节 → 再写后端代码 | 契约改动先落 `app/core/models.py` 并同 PR 回写架构文档第三章；PR 标题带子阶段编号，如 `feat(pipeline): 1.1 ingestion scanner` |
| **S2 前端同步/实现** | 先读「前置阅读」中的前端章节 → 再动前端代码 | 前端 `types/api.ts` 由后端 OpenAPI 经 `openapi-typescript` 生成、禁止手改（J25）；02 §7 为人读镜像，冲突以 OpenAPI 为准；变更后须重跑 `pnpm gen:api` 并提交生成物。界面交付按各单元指定执行 |
| **S3 测试验收** | 先读 07 对应用例节 → 执行单测/接口用例/E2E | 指定用例全过；命中 D8 门禁条件（触及分块/清洗/检索/模型）时跑 golden 回归 |

通用规则：
- 顺序强制：S1 自检未过不得进入 S2；S3 不通过回退到出错步骤修复后重跑
- 「前置阅读」是硬门槛——未读不开工；文档与实现不符当天提修正 PR（§9）
- 单元粒度 = 一个可独立验收的 PR 组（通常 ≤5 个工作日）
- **全局 DoD（叠加在每个单元准出之上）**：模块单测通过 + golden set 该环节指标不低于基线 + LangSmith trace 可完整回放该链路
- **契约测试门禁（J25）**：每个单元 S3 必过 4 类可执行契约——`openapi_vs_02` / `sse_schema` / `degraded_parity` / `errorcode_parity`（断言来源见 09 §4）；`types/api.ts` 由 `openapi-typescript` 生成、禁手改（06 §2）。任一契约失败即视为 S3 未过，回退修复重跑。

## 7. 配置变更流程（J18 边界）

| 变更类别 | 流程 |
|----------|------|
| 清洗规则 / 检索权重 / 降级参数 / agent.* 效率参数 | `PUT /admin/config/hot-reload` 热更（写回 YAML + pydantic 重校验），无需重启 |
| 记忆层 `memory.*`（reliability.yaml：l1_hit_threshold / dedup_similarity_threshold / working_turns / wm_max_turns 等） | **冷启动生效**（构造期注入 MemoryStack）；调整命中阈/去重阈后须回归 A-10/A-11 用例 |
| 分块参数 / embedding 模型 | **禁止热更**——走"改 YAML → 全量重建索引 → golden set 回归 → 发布"流程 |
| models.yaml（注册表/角色/fallback） | 不支持热更：修改后需重载连接池，随发版生效 |

热更操作记录自动落审计日志（操作人/时间/diff）。

## 8. 缺陷管理

| 级别 | 定义 | 响应 SLA |
|------|------|----------|
| P0 | 主链路不可用 / 数据损坏 / 安全漏洞 | 立即修复，当日热修 |
| P1 | 核心功能错误（答非所问、引用错位、降级未标注） | 24h 内 |
| P2 | 非核心功能或体验问题 | 下个迭代 |
| P3 | 优化建议 | 排期评估 |

流转：新建 → 分级确认 → 修复分支（fix/*）→ 回归验证（07 用例回放）→ 关闭。点踩 bad case 强制回流 golden set（第九章反馈闭环）。

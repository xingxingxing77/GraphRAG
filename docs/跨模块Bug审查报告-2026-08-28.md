## Critical（6 个）

### C1. load_memory 节点读写错 state 通道：多轮会话第 2 轮起用户当前问题被丢弃
- **两端证据**
  - 写端：`app/agent/nodes/load_memory.py:64` — `return {"query": f"{context_text}\n\n{state.get('query', '')}"}`；`:30` episodic 检索向量也取 `state.get("query", "")`。
  - 契约：`app/core/models.py:644-663` — `ChatRunInput` 只有 `original_query/session_id/user_id`，**run 入参从不设置 `query`**；前端 `rag-web/src/hooks/useChatStream.ts:143` 同样只传 `original_query`。
  - 读端：`app/agent/nodes/query_understanding.py:33`、`planner.py:117`、`generator.py:130` 均为 `state.get("query") or state.get("original_query")`。
- **后果**：首轮 `query` 为空 → 注入内容变成 `context + ""`（当前问题消失）；第 2 轮起 `query` 残留上一轮 checkpoint 的旧改写查询（truthy）→ `original_query` 永远不再被读取。planner/generator 在"只有历史、没有本轮问题"的文本上作答，答非所问。单测掩盖了它：`tests/test_agent/test_nodes_memory.py:56` 手工传了 `query`。
- **修复**：`load_memory.py` 以 `state.get("original_query") or state.get("query", "")` 为基准（`:30` 与 `:64` 两处）；或规定 `query` 通道仅承载"改写产物"，改写前一律读 `original_query`。

### C2. 前端 streamMode 缺 `values`：聊天终态答案/引用/降级原因永远不到达
- **两端证据**
  - 请求侧：`rag-web/src/lib/agentClient.ts:56` — `streamMode: ["updates", "messages-tuple"]`。
  - 消费侧：`rag-web/src/hooks/useChatStream.ts:190-196` — 仅 `event === "values"` 才 `chat.setFinalAnswer(...)`；`rag-web/src/lib/summarize.ts:79-95` 从 values 提取 `answer/citations/degraded_reasons`。
  - 服务端事实：langgraph-api 仅下发被请求的 stream_mode（`.venv/.../langgraph_api/stream.py:434-441`）。
- **后果**：真实 run 路径只有 thought 步骤帧，流结束后不渲染答案、不写引用；`TIER_TIMEOUT_MS` 内 values 未到还会误报"回答超时"。主链路不可用。
- **修复**：`agentClient.ts:56` 改为 `["updates", "values", "messages-tuple"]`（fast 档另加 `"messages"`，见 M-fast）。同时修正 `docs/03_通信协议规范.md:75` 与 `:83` 的自相矛盾表述。

### C3. 检索集线器把记忆集合 `rag_cache`/`rag_episodic` 当业务集合检索 → 高分空内容伪证据污染
- **两端证据**
  - `app/agent/nodes/tool_router.py:310`、`app/api/endpoints/debug.py:160`：`[c for c in await qdrant.list_collections() if c.startswith("rag_")]` — 无排除。
  - 权威口径：`app/pipeline/indexing/pipeline_service.py:111` — 同前缀但显式排除 `("rag_cache", "rag_episodic")`。
  - 记忆集合 payload 只有 `question/answer/...`（`semantic_cache.py:248-259`、`episodic.py:113-121`），**无 `content/chunk_id/doc_id`**。
- **后果**：写过 L1 缓存后，dense/sparse 路返回"空 content + 超高分（与当前问题相似的历史问题，cosine 常 >0.9）"的伪证据；`generator.build_evidence_block` 产出 `[n] `（空引用）；融合按 `content:sha256("")` 把所有空内容错误合并成一条。
- **修复**：两处枚举复用 `pipeline_service.py:111` 的排除口径（建议收敛为 `qdrant_client.py` 单一常量/工具函数）；并在检索器侧丢弃 payload 缺 `content` 的命中。

### C4. Sparse 检索路在 Agent 主链路恒为空：索引侧写了 sparse 向量，查询侧永远查不到
- **两端证据**
  - 查询侧：`app/agent/nodes/tool_router.py:305-309` — hub 硬编码 `flag_client=None`。
  - 降级链：`app/embedding/service.py:137-139`（None → sparse 返回 `[{}]`）→ `app/retrieval/sparse_retriever.py:99-100`（空 → 返回 `[]`，静默、无告警、无 error 计数）。
  - 对照：`app/api/deps.py:163-172` 会尝试构建 `FlagClient()`（admin 索引与 debug 均走它）。
- **后果**：`vector_indexer.py:126-133` 为每个 chunk 写入的 sparse named vector 在生产查询路径无人读取，六路混合检索退化为五路。
- **修复**：hub 复用 `await deps.get_embedding_service()`（与索引/debug 同一单例），或同样尝试构建 `FlagClient` 并在失败时打点。

### C5. docker-compose 只给 agent 服务加了容器网络 env 覆盖，app（业务面）服务被遗漏
- **两端证据**
  - `docker-compose.yml:12-31`（app 服务仅 `env_file: .env`，无 `environment:`）；`:41-53`（agent 服务有完整覆盖）。
  - `.env` 全部是宿主机视角：`QDRANT_HOST=localhost`、`REDIS_HOST=localhost`、`ELASTICSEARCH_HOST=http://localhost:9200`、`NEO4J_URI=bolt://localhost:7687`、`POSTGRES_DSN=...@localhost:5433`。
  - `app/core/config.py:148-178` 默认同视角；`LANGGRAPH_SERVER_URL` 在 .env 与 compose 均未定义（默认 `localhost:8001`，容器内错）。
- **后果**：`docker compose up` 后业务面容器内 Qdrant/Redis/ES/Neo4j/Postgres/langgraph/Ollama 全指向自身 localhost：`/ready` 全 down 503、sessions 代理失败、embedding 不可用。
- **修复**：给 app 服务补同一份 `environment:`（含 `LANGGRAPH_SERVER_URL: http://agent:8001`），或用 YAML anchor 统一两服务 env。

### C6. `latency_tier` / `model` 经 `config.configurable` 传入，但 app/ 内零处读取 — 显式定档与请求级模型覆盖完全失效
- **两端证据**
  - 发送：`useChatStream.ts:144` — `{ latency_tier: tier, model: ... }` 只进 `config.configurable`。
  - 消费：`app/agent/nodes/query_understanding.py:35`、`routers.py:152`、`tool_router.py:225` 只读 `state["latency_tier"]`；`generator.py:148` 固定 `chat_with_fallback`，`registry.for_model()`（`registry.py:195`）全仓零调用；grep `app/` 无任何 `configurable` 读取。
- **后果**：用户选的 fast/standard/deep、precheck 建议档位、前端模型选择全部被静默忽略；fast 档 A2 短路、deep 档并行扇出永不按用户选择生效。
- **修复**：把两字段加入 `ChatRunInput`（并同步 `AgentState` 契约，02/03 同 PR），由 run input 并入 state；generator 按 `state["model"]` 走 `registry.for_model()` + fallback。注意 `state.latency_tier` 是 `Literal["fast","standard","deep"]`，"auto" 需在入口解析。

## Major（10 个）

### M1. generator 降级分支丢弃重试计数 → `generator ↔ self_correction` 可循环至 recursion_limit
- `app/agent/nodes/generator.py:134-139` 把 `self_correction_retries+1` 写进局部 `updates`；`:157-165` LLM 异常分支直接 `return {...}` **丢掉 `updates`**；`routers.py:199-204` 以 `retries < 1` 判回环 → 降级文案每轮打分都低 → retries 恒 0 死循环，直到 langgraph server 默认 25 层兜底 500。
- **修复**：异常分支的返回 dict 也带 `self_correction_retries`（与 token_usage 一样提出到公共增量）；或把计数持久化移到 self_correction 节点。

### M2. 六路检索 score 口径不可比，却按统一 0-1 阈值消费（A2 短路 / B3 修剪 / E1 排序）
- 生产端：ES BM25 原始分（`es_client.py:229`，无界 ≥1）、global `1.0 + overlap`（`global_retriever.py:113`）、graph 恒 1.0、web `1.0 - i*0.05`、dense/sparse 余弦 0-1。
- 消费端：A2 短路 Top-5 均分 ≥ 0.7 即跳过反思（`routers.py:157-164`，配置注释还写着"平均 Rerank 分"，`pipeline_config.yaml:130`）；B3 修剪 `score < 0.25`（`tool_router.py:243-247`）；E1 排序 `-r.score`（`generator.py:60`）。
- **后果**：含一条 BM25/global 结果 A2 几乎必然短路（反思回环形同虚设）；弱 BM25/低余弦证据被 B3 误剪。
- **修复**：各检索器出参归一化到 [0,1]（min-max 或 rank 归一），或在 `RetrievalResult.metadata` 标 `score_kind`，消费端只比较同口径分数。

### M3. self_correction 未按契约把失败原因注入重生成 — 重试是同一 prompt 原样重放
- 契约：`self_correction.py:5-6`（"分数低于阈值时注入失败原因供 Generator 重生成"）；实际 `:108-113` 只返回 `{"faithfulness_score": score}`，judge 的 `reason` 在 `_parse_score`（`:44-66`）被丢弃；generator prompt 不消费任何失败原因，state 也无对应字段。
- **后果**：低分触发重试必然产出同样答案、同样低分，纯浪费一次 LLM 调用。
- **修复**：`_parse_score` 同时返回 reason；self_correction 输出 `correction_hint`（复用或新增 state 字段）；generator 重入时把 reason/score 拼进 user_prompt。

### M4. DELETE /sessions 不级联清理记忆（docstring 声称级联）
- `app/api/endpoints/sessions.py:81-106` 只调 `thread_store.delete_session`；`working_memory.clear()`（`working_memory.py:102-108`）与 `episodic.delete_by_session()`（`episodic.py:179-186`）全仓零调用，两者的 docstring 都写着"DELETE /sessions 级联（07 A-05）"。
- **后果**：删会话后 Redis `wm:{session_id}`（TTL 7 天）与 `rag_episodic` 点（保留 180 天）成孤儿；情景记忆继续带旧会话片段且 `exclude_session` 失效。
- **修复**：delete 成功后经 `get_memory_stack()` 调 `working_memory.clear(session_id)` + `episodic.delete_by_session(session_id)`（失败仅告警，不阻断 204）。

### M5. 缓存失效联动漏掉 fulltext 路：write_back 只读 `metadata["doc_id"]`，fulltext 的 doc_id 在顶层
- `app/agent/nodes/write_back.py:34-36` 只取 `(metadata or {}).get("doc_id")`；`app/retrieval/fulltext_retriever.py:123-124` `doc_id=src.get("doc_id")`（顶层），metadata 只含 `entity_id/canonical_name`。
- **后果**：靠 fulltext 召回支撑的缓存答案在文档更新后不被 `SemanticCache.invalidate_doc` 失效，用户继续拿到旧答案。
- **修复**：`_matched_doc_ids` 优先读顶层 `getattr(evidence, "doc_id", None)`，metadata 作回退（兼容 dict 形态）。

### M6. 语义缓存 L1 键不含 embedding 模型/版本 → 换模型即缓存污染
- `app/memory/semantic_cache.py:242-261`：`point_id = uuid5(namespace, normalize(question))`，payload 无 embedding 模型标识；写入在 agent 面（`write_back.py:79-88`）、读取在业务面（`chat.py:65`），两侧 embedding 配置无任何约束机制（`EMBEDDING_MODEL` 可 env 覆盖，`config.py:151`）。
- **后果**：换 embedding 模型后旧点向量与新查询不同语义空间，top-1 ≥0.95 仍可能命中返回无关旧答案。
- **修复**：payload/point_id 材料加入 `embedding_model`（与维度），读取侧用 Filter 过滤；或按模型命名集合。

### M7. dense-only 调用方全部误用双通道 `embed()` — API 进程内反复加载/运行 BGE-M3 稀疏编码器
- `semantic_cache.py:132`、`episodic.py:103/145`、`scheduler.py:130`、`dense_retriever.py:112`、`sparse_retriever.py:98` 均调 `embed()`；service 专门提供了 `embed_dense()`（`service.py:82-92`）却无人使用。
- **后果**：装了 FlagEmbedding 的部署里，每次 precheck 缓存查询/记忆检索/dense 检索都触发稀疏编码并被丢弃，且全程持有全局 semaphore——dense 检索外层 3s 超时大概率因此超时降级。
- **修复**：dense-only 消费方改 `embed_dense()`。

### M8. 检索 hub 单例永久缓存集合快照与私有客户端
- `tool_router.py:281`（模块级 `_hub`）、`:293-295`（命中即返回）、`:300-310`（集合列表只枚举一次；四个客户端非 deps 单例）。
- **后果**：admin 重建/新增 `rag_{doc_type}` 集合后，重启前 dense/sparse 检索不到；hub 客户端游离于 `deps.close_all_clients()`（`deps.py:243-259`）之外，连接池泄漏；与 deps 是两份 embedding 实例（双 semaphore/连接池）。
- **修复**：hub 复用 deps 客户端单例；集合列表在每次 retrieve 时惰性刷新；shutdown 一并关闭。

### M9. `ESSyncer.sync_entities` 无生产调用方 → `rag_entities` 索引恒空，J6 协同失效
- 定义 `fulltext_indexer.py:40`；唯一管线调用 `pipeline_service.py:167` 只调 `sync_chunks`；消费侧 `fulltext_retriever.py:140` 首选 `rag_entities`、空则回退 `rag_chunks`。
- **后果**：实体索引恒 0 条，`_neo4j_expand` 一跳扩展（`:110-115`）从不触发，BM25 口径退化为全文匹配。
- **修复**：`index_documents` 收集本批 `chunk.entities`（canonical/type/zone/description）调 `sync_entities`；或删除该路与 `rag_entities` 检索分支，消除半接线。

### M10. prompt_bar 写端点完全无鉴权
- `app/api/endpoints/prompt_bar.py:119-135,138-159,162-192`（`POST /skills`、`/skills/upload`、`/attach` 落盘文件系统）无 `get_current_user/require_admin`；对照全站其余写端点均有鉴权。

## 存疑（设计意图需确认，暂不定级）

1. **no-memory 降级答案会写入 L1 缓存**：`load_memory.py:61` 失败只报 `degraded_reasons=["no-memory"]` 不置 `degraded=True`；`write_back.py:50` 只查布尔 → 带 `X-Degraded: no-memory` 的响应仍入缓存，precheck 命中返回时不带降级标记（`chat.py:80-87`）。若有意为之需写入文档。
2. **checkpoint 反序列化 dict 形态兼容不一致**：`write_back.py:24-37` 专门防御 dict 形态，但 `tool_router.py:120`、`generator.py:60`、`routers.py:160` 假定 pydantic 对象，若 serde 走 JSON mode 会 AttributeError。
3. **GraphRetriever 用整句原始查询做 `CONTAINS $query` 子串匹配**（`graph_retriever.py:29`）——中文长查询几乎不可能命中实体名，graph 路接近恒空；属设计缺陷。
4. **GlobalRetriever 召回与查询无关**（`global_retriever.py:28-34` 仅 level DESC LIMIT）——同理。
